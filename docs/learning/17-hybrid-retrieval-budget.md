# 第十七课补充：混合检索为什么需要分配阶段预算

一次工具调用的超时是整个请求的预算，不是每个步骤都可以重新使用的时间。混合检索会经过索引检查、向量召回、关键词召回、融合和当前可见性校验。若向量召回独占全部剩余时间，关键词路线即使可以正常查询，也没有时间完成。

## 本次修复

`RetrievalService.boundedVector` 为向量路线建立独立子截止时间，包含线程排队、Embedding 和向量 SQL。它复用现有两线程、八队列的可选阶段线程池；超时会取消 Future，并清除取消的排队任务，不创建无限线程。

- hybrid 给后续关键词 SQL 与当前可见性校验保留约三分之一剩余预算，至少 250ms。
- vector-only 仅给最终校验保留约十分之一剩余预算，至少 50ms；失败时不会使用关键词结果。
- 预算不足以启动向量路线时，hybrid 明确记录 `VECTOR_CHANNEL_FAILED`。响应的请求模式仍为 hybrid，命中来源会显示实际使用的 keyword 通道。
- 权限拒绝、调用方取消和总截止时间到期会终止请求，不能当作普通通道降级。

这里只降级召回通道，没有切换内存数据库、增加重试或延长 MCP 的 10 秒协议上限。关键词结果仍来自当前 PostgreSQL 数据，并经过最终可见性校验。

## 结合代码阅读

1. 从 `retrieve` 的全局 `RetrievalDeadline` 开始，找到向量、关键词和最终校验的顺序。
2. 阅读 `boundedVector`：子截止时间在入队前创建，所以排队也消耗该路线预算；进入工作线程后重新检查权限与剩余时间。
3. 找到 `finally` 的取消与队列清理。超时不仅意味着“不再等待”，还需要尽量停止实际工作。
4. 比较通道失败和全局过期：前者可以在仍有总预算时降级，后者必须向上抛出。

取消依赖底层 I/O 响应中断和超时。故意忽略中断的实现可能暂时占住有界工作线程；实现不声称能强行终止任意 Java 代码。
