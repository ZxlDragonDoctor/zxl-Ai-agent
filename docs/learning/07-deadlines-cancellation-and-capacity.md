# 第七课：截止时间、取消与并发容量

日期：2026-10-21。前置：[第六课实现记录](06-implementation.md)。本文件是第七课任务包与验收基线；实现和验证范围见[第七课实现与验收记录](07-implementation.md)。

本课目标：让任务知道还能执行多久、什么时候应停止、能占用多少资源。连续完成六项关联任务，建议安排 6–8 小时，分两批实现，最后集中验收。前端由助手负责。

## 1. 先理解第六课解决到了哪里

第六课已经保证：等待超时后，Task 的 FAILED 终态不会被迟到成功覆盖；Agent 会等底层调用真正结束后再释放占用。

但当前仍有以下情况：

- 规划、工作任务、汇总分别等待 60 / 120 / 60 秒，没有共享的总截止时间。
- HTTP / SSE 等待 300 秒后结束，后台可能继续工作。
- cached thread pool 与工作角色的 commonPool 调用缺少统一容量预算。
- 同一实例忙碌就报错，没有有界排队；capability.maxConcurrency 只是声明。
- 用户不能按 executionId 请求取消，也不能查询取消后的实际清理进度。

**终态保护负责“结果不被改写”；本课控制“后续工作是否还会启动、资源何时真正释放”。**

## 2. 四个概念要分清

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 请求等待超时 | 当前连接不再等待结果 | 浏览器请求结束，后台可能仍在执行 |
| 执行截止时间 | 整个业务运行最晚应停止启动新工作 | 从接收目标起总共允许 90 秒，排队也计时 |
| 协作取消 | 执行路径检查取消信号，并停止后续动作 | 每轮调度、模型调用前、工具副作用前检查 |
| 实际资源释放 | 底层调用已经返回或确认停止，占用才可归还 | HTTP 还没结束时，工作实例和调用许可仍被占用 |

Java 17 的 CompletableFuture.cancel 以异常完成 Future，并不直接控制产生结果的计算；其 mayInterruptIfRunning 参数在这个实现中没有中断效果。因此，需要沿应用执行链传递停止信号，并检查实际客户端的取消能力。[Java 17 官方文档](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/CompletableFuture.html#cancel(boolean))

## 3. 本课必须成立的不变量

1. 排队、规划、工作任务和汇总共享一个运行截止时间；子任务只能缩短它，不能延长它。
2. 取消或截止时间生效后，不再领取新的工作任务，不再开始后续模型 / 工具调用。
3. 已完成任务保留原结果；未完成任务按原因进入取消或超时终态，不能覆盖第六课已有终态。
4. 返回“取消已接受”不表示所有底层调用已停止；页面如实显示剩余占用。
5. 一个工作实例的一份执行许可只能被持有一次、释放一次；不能因为等待 Future 被取消就提前归还。
6. 全局并发、角色并发、排队长度和排队时间都有明确上限，超限请求得到可解释结果。
7. 停止信号和执行许可属于运行时控制对象，不进入 userInput，也不序列化给模型。

## 5. 六项工程任务

### 任务一：建立共享执行截止时间

设计 ExecutionDeadline / ExecutionControl，保存服务端接受时间、总预算、取消原因及剩余时间计算方法。

- 服务端配置默认预算和最大预算，校验客户端请求值，不能允许无限期执行。
- 一个运行只创建一次总 deadline；子任务等待上限为 min(任务上限, 运行剩余时间)。
- 排队时间计入总预算；任务出队时必须再次检查。
- JVM 内用单调时钟计算剩余时间，墙上时间用于展示；不能把 nanoTime 值当作可跨重启恢复的时间戳。
- 用可控时钟验收，避免靠长时间 sleep 制造超时。
- 对规划、普通任务、额外汇总使用同一计算入口，移除散落的固定秒数。

交付：一张三层时间图，说明运行预算、任务预算和底层客户端超时的关系。

### 任务二：实现运行登记与协作取消

设计单进程 RunRegistry，按 executionId 登记 ExecutionControl、当前阶段、任务及实际占用。

- 请求开始时登记；记录取消请求与实际清理结果；终态记录有保留期限和容量限制。
- 新增取消入口，例如 POST /api/ai/multiagent/runs/{executionId}/cancel，响应明确区分“已接受取消”“已经结束”“不存在”。重复取消不重新执行结束逻辑。
- 调度前、领取实例前、开始模型调用前以及后续工具动作前检查控制信号。
- 取消一项运行不影响别的运行，不向其他会话的工作对象广播 shutdown。
- 已完成的任务不变；未完成的任务通过 TaskLifecycle.cancel 决定终态，WorkflowOutcome 明确区分 cancelled 与 failed。
- 只在登记表中传递控制对象，不用 Task.input 或 Prompt 传递取消 token。

本阶段仍是单用户本地演示。生产环境的运行归属与取消权限要在身份 / 租户课程接入，不能凭知道 executionId 就获得操作权。重启恢复也尚未实现。

### 任务三：处理底层调用和资源清理

对当前 Spring AI Alibaba M6.1 / ChatClient 的实际调用链检查可配置的连接、读取超时及取消支持，以仓库依赖为准。

- 对支持取消的操作传递真实取消信号；不支持取消的阻塞调用使用明确超时，并记录尚未结束的占用。
- 用执行租约或等价的所有权对象管理许可，完成和取消路径只能成功释放一次。
- 用户已收到取消结果，但底层仍未结束时，保留 BUSY 和实际调用计数；不能让同一实例又开始下一项任务。
- 工作线程中断需要正确传递或恢复标记，不吞掉中断后继续下一次外部调用。
- 模型响应、事件投递或清理回调失败时，也要归还真正已经结束的资源；不得重新打开 SHUTDOWN 实例。
- 取消不能回滚已经发生的外部写入。第八课的幂等与后续审批仍然必要。

交付：分别描述“可协作停止”“不可中断但有限超时”的真实行为，不宣称一种取消方式适用于所有模型和工具。

### 任务四：用容量与有界排队控制并发

用明确的线程池和许可替换无限扩张的调度方式。容量至少覆盖：并行运行数、各角色工作实例、实际模型调用数、队列长度。

- 线程池和队列上限通过配置提供；排队满时返回 AGENT_CAPACITY_EXCEEDED 或约定的结构化错误。
- 任务只有拿到资源并成功领取后才进入 IN_PROGRESS；排队期间保持 PENDING，并报告 queued 阶段。
- 排队截止或取消后移出等待队列，不能在用户已经收到终态后突然出队执行。
- 保留第五课业务依赖图，不能把资源等待伪造为新的任务依赖。
- 区分等待线程、工作线程和阻塞 I/O，避免同一小线程池中父任务占满线程等待子任务的死锁。
- 定义公平性和拒绝策略；不要静默丢弃任务，或无限制重试抢占实例。

有界队列与明确拒绝策略是 ThreadPoolExecutor 提供的机制，具体大小仍需要业务负载和容量实验决定。[Java 17 官方文档](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)

交付：一份演示配置和资源时序图，说明每个许可在哪里获取、由谁归还。

### 任务五：接入页面与结果契约

前端由助手实现，你负责服务端状态语义。

- 页面显示排队、执行、请求取消、已取消及等待底层清理等实际情况；只提供取消当前 executionId 的按钮。
- 用户点取消后保留已完成任务、实际失败 / 取消原因与时间，不清空历史来掩盖结果。
- 断开页面连接默认只停止接收；用户主动取消才触发业务取消入口。这一策略写入接口说明。
- 取消按钮不以关闭 SSE 作为成功依据，必须读取服务端回执与最终 outcome。
- Task 完成比例、运行终态、剩余底层占用分开展示，沿用第六课事件序号和终态保护。
- 本课用单进程登记表查询当前状态；持久化、完整事件重放和多实例协调继续留后续课程。

### 任务六：集中验收与容量实验

先用可控替身执行下表，再做少量真实模型调用。替身可控制开始时机、返回时机、是否响应取消和剩余时间，不用随机延迟作为通过依据。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 排队期间总预算耗尽 | 不发起模型调用；终态与排队原因明确 |
| 规划阶段取消 | 不启动业务工作角色 |
| A、B 运行时取消 | 不启动后续 C，已完成结果保留 |
| 不支持中断的调用收到取消 | 用户获得取消结果，实例仍占用至真实结束 |
| 底层迟到成功 | 不覆盖取消 / 超时终态，只执行必要清理 |
| 取消已完成运行，或连续取消两次 | 原 outcome 不变，不重复释放许可 |
| 并发达到上限，再提交目标 | 有界排队或明确拒绝，不无限增加线程 |
| 队列中取消，随后释放容量 | 被取消的任务不会出队执行 |
| A 取消，B 属于另一项运行 | B 正常执行，不受 A 的停止信号影响 |
| 清理或事件订阅者异常 | 资源与业务状态仍收敛，错误可以追踪 |

容量实验记录：输入并发数、实际执行并发、队列峰值、拒绝数量、完成数量、取消后仍在清理的数量及最大线程数。不要只展示平均耗时，也不根据一次结果承诺生产吞吐。

## 6. 两批推进与提交

第一批完成任务一、二、三：共享控制对象、运行登记与取消入口、底层清理和超时边界。

第二批完成任务四、五、六：有界容量、双语页面、专项矩阵和容量记录。按控制契约、资源实现、API、页面、验收文档细分提交并 push，最后核对远程。

## 7. 面试复盘

1. 为什么 HTTP 超时、任务超时和底层停止是三件事？
2. CompletableFuture.cancel(true) 为什么不能证明模型请求已经被终止？
3. 用户已经收到取消结果，Agent 为什么可能仍然 BUSY？这时能否释放并发许可？
4. 总预算剩 2 秒，为什么不能再给下一项任务一个独立的 120 秒？
5. 线程池有最大线程数，但队列无限长，会发生什么？
6. 取消与任务正常完成同时发生，谁决定终态？怎样避免双重归还？
7. 为什么服务重启后，内存中的取消登记与执行租约不足以保证一致性？
