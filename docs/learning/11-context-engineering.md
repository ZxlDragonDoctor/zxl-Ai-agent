# 第十一课：上下文工程、裁剪与可追溯摘要

## 先抓住一个问题

第四课把会话保存下来，让刷新页面后仍有历史。第十一课解决另一件事：**历史很多时，这次调用应该给模型看什么？** 数据库存了十万条记录，不代表一次接口响应要返回十万条；模型上下文也需要服务层做选择与组织。

本课先修是第四课。第十课 Temporal 是另一条持久工作流实践线，尚未实现，不妨碍本课；跳到本课不表示第十课自动完成。

## 三种对象不要混淆

| 对象 | 本项目中的意义 | 生命周期 |
| --- | --- | --- |
| 原始历史 | 用户消息、助手消息、工具调用及真实结果 | JSON 会话仓储保存，不因预算裁剪而删除 |
| 本次上下文 | 从历史中选择的完整轮次、摘录与证据 | 每次请求重新组装的派生视图 |
| 长期记忆 | 可更正、可删除、带身份范围的用户事实 | 第十四课继续实现，本课摘录不能冒充长期记忆 |

## 预算先留位置，再放材料

```text
模型窗口
  = 系统提示与当前问题
  + 工具定义、框架开销等预留
  + 历史消息、工具结果、证据、摘录
  + 输出预留
```

输出预留是组装时留空的位置，不代表模型一定输出这么多，也不代表已经设置供应商的输出上限。真正的请求还要按模型配置输出限制，读回实际 usage 核算。

本次采用可替换的 UTF-8 字节估算，带固定消息开销。它让中文、英文与 emoji 的离线预算有一致可重现的计算规则，**不是精确 tokenizer，也不是计费数据**。不同模型的分词、请求包装与工具 schema 都可能改变实际消耗；上线前要用具体模型校准，并在每次模型调用前控制预算。

系统提示与当前用户问题属于必要输入。必要输入超限应返回明确错误，不能默默删掉一半业务要求。可选历史按完整 run 选择；工具结果还受自己的分类预算约束。

## 为什么以完整轮次为单位

假设一轮是：

```text
user：查工单 T-42
assistant：tool_call(id=c1, name=findTicket)
tool：tool_call_id=c1, result=待审批
assistant：这张工单还在等待审批
```

如果只截取最后三条，用户的问题丢了；只留下 tool，没有对应调用，协议可能无效；只保留调用而删掉结果，又会产生未回答的工具调用。预算分配首先保护消息组完整性，而不是按字符串长度截断任意消息。

完整并不等于真实：工具参数中工单号正确，不代表工具输出准确；历史助手的判断也不能当成业务数据库的权威状态。

## 摘录式摘要：先做到可核查

本课采用确定性原文摘录，不额外调用摘要模型。每条摘录必须绑定 runId/messageId 和原文，摘要模板与估算策略也有版本，便于复现。

检查能够证明“这段文字来自这条历史”，不能证明“历史说的是事实”，也不能证明“所有关键事实都被保留”。一个重要否定词、时间条件或随后修正的消息都可能改变含义，因此要把原文、角色、时间和最近轮次一起检查。

不能把历史摘录包装成高权限系统规则。原文即便写着“忽略系统提示”，它仍是历史材料；消息角色隔离也不能单独保证防住所有提示注入。

## 用一个案例学习取舍

固定工单案例：用户最初说“周五发布”，后来修正为“审批通过后才能发布”；工具最近返回“未审批”。比较三种输入组织：

1. 原始长历史：信息多，但成本高、可能超窗口。
2. 摘录加最近完整轮次：节约预算，但要检查修正条件、工单 ID 和工具结果有没有遗漏。
3. 相关记录优先：围绕当前问题选材料，但“相关”的判定需要单独的检索策略；本课不把顺序筛选宣传成语义检索。

先比较预算报告、保留/排除来源与事实覆盖；真正的答案质量、时延、实际 token 与缓存效果，需要使用固定模型和同一组问题另做实验。本次没有真实模型对照，不填写虚构收益。

## 本项目阅读顺序

1. `conversation/model/Conversation.java`：看完整历史与 run 如何存储。
2. `conversation/service/ConversationMessageMapper.java`：看工具调用 ID 与结果如何恢复。
3. `conversation/context/`：看预算、选择、摘录与报告的实现。
4. `conversation/service/ConversationContextWindow.java`：看旧最近轮次窗口怎样复用组装服务。
5. `conversation/service/AgentConversationService.java`：看统一会话怎样带着本次问题准备历史，并防止派生摘录写回原始历史。
6. [实现、操作与测试证据](11-implementation.md)：按实际代码的参数与入口操作。

这套接入控制统一会话请求开始时的历史。不能由此推断旧 LoveApp 的所有接口、多 Agent、ZxlManus 每个内部步骤都已经有动态上下文治理；具体边界以验收记录为准。

## 你这一课要独立完成什么

- 从一个预算报告中指出：必要输入、输出预留、分类预算、实际选入与被排除的来源。
- 调小历史预算，解释为什么整轮工具交互消失，而不是只消失一条 tool 消息。
- 改写一条原始历史，再检查旧摘录是否仍可接受；解释引用验证与事实验证的区别。
- 用中文和 emoji 输入跑预算案例，解释为何字符数、字节数和 token 不能互换。
- 根据失败用例修改一处预算策略，保持原始会话历史不变，并运行相关测试。

## 面试表达

**问：为什么有了聊天记忆还需要上下文工程？**

仓储保存可追溯历史，模型每次调用只能接收有限输入。服务层按预算与业务优先级选择完整轮次，保留工具协议和来源；必要输入放不下明确拒绝。实际 token 由模型 usage 校准，不把估算当计费。

**问：摘要能保证不遗忘吗？**

不能。摘录能验证来自原文，但仍可能漏掉修正或条件；生成摘要还可能改写事实。应保留来源与版本，用固定业务案例检查关键事实，并支持回原文。本课验证出处和预算，不声称已证明语义完整。

**问：怎么验证效果？**

先用自动测试保护预算、工具消息完整性、原文出处和存储不变，再用固定模型对照遗漏、时延、usage 与答案质量。自动测试通过和真实模型业务效果是两种证据。
