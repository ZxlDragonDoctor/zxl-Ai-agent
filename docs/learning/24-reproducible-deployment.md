# 第 24 课：从本机运行到可复现交付

本课是下一课的完整任务，尚未完成部署验收。目标是在干净检出中启动正式身份、PostgreSQL + pgvector、主应用、知识 Worker、MCP 和前端，独立核对迁移、权限、模型调用、预算及重启恢复。不能依赖开发者 target 中的历史 class 副本。

## 核心概念

构建成功只说明产物生成；就绪检查需要确认应用能访问必要依赖。存活检查用于判断进程是否需要重启，不能因为模型暂时限流就反复重启整个应用。可复现交付必须同时固定源码版本、运行时、依赖和迁移，并说明哪些外部模型无法固定权重版本。

现有根 Dockerfile 用 JDK21 构建，pom.xml 的 java.version 为17；前端采用浮动 node:20-alpine 和 nginx:alpine，安装命令是 npm install。它们是现有基础，不是已通过的固定部署基线。现有 PORT 注释也必须通过真实启动验证，不能假定 PORT 自动等同 server.port。

## 完整工程任务

1. 清点正式服务角色、入口端口、数据库权限及配置来源；提供不含密钥的环境模板，缺少必要变量必须启动失败，禁用内存数据库回退。
2. 选择并记录一致的 JDK、Node、PostgreSQL、pgvector 和镜像版本；使用锁文件安装前端依赖，记录镜像摘要与构建源码提交。Spring AI M6 升级另开兼容任务，不与交付环境重构混为一笔。
3. 构建主服务、Worker、MCP 与前端产物，定义依赖就绪探针和有界启动等待；前端反向代理覆盖认证 cookie、CSRF、SSE 和长请求。
4. 用全新数据库执行迁移；已有库再次启动不得重复迁移。应用身份不能持有不必要的数据库管理权限；备份恢复必须核对版本和数据。
5. 执行两租户登录、检索隔离、无证据拒答、审批写入与回执重放、预算耗尽和SSE重连。真实模型证据与可控故障夹具分开保存。
6. 重启应用与Worker，确认已落库的报告、审批回执、预算状态及个人学习进度保留；UNKNOWN不得因重启退款。
7. 建立自动检查流水线，输出版本、测试结果、迁移状态及失败原因。回滚应用前检查新旧数据库兼容性；不能直接删除新迁移记录冒充回滚。

## 验收矩阵

| 场景 | 需要的实际证据 |
| --- | --- |
| 干净检出启动 | 提交号、锁定版本、构建日志与全角色就绪状态；不能引用本机旧class |
| 配置缺失 | 不打印凭据的明确错误与非零退出 |
| 空库 / 已有库 | 首次迁移成功、再次启动无重复迁移 |
| 跨租户和审批 | 两身份浏览器操作、独立PG核对与脱敏截图 |
| 故障 / 重启 | 停止依赖后的状态、恢复结果、零重复业务写入 |
| 浏览器 | 登录、语言、图谱2D/3D、阅读卡、业务执行、重连逐状态截图 |
| 回滚 | 兼容性检查、恢复步骤与实际演练结果 |

所有记录注明环境、时间、配置边界及失败，不把未执行的模型请求或容器启动写成通过。最终交付运行说明、配置模板、固定部署定义、自动验收脚本及证据目录。

## 面试练习

为什么本地能跑不等于能部署？为什么readiness失败不一定触发重启？数据库迁移成功后如何安全回滚旧应用？如何在交付时证明没有把本机密钥、缓存和历史class带进去？
