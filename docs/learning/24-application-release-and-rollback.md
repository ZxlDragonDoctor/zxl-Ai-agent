# 第24课：应用发布、版本回退与数据兼容

回退镜像并不会自动撤销数据库迁移。旧程序若不理解新schema或新文件格式，盲目回退会把部署故障变为业务故障。本单元在原有低权限容器、独立迁移和成对备份基础上，增加候选检查与有序镜像切换。

## 项目中的实现

`SchemaVerifier` 是独立Java命令，参数显式指定security和knowledge，读取运行身份的数据库配置。它只调用已有`DatabaseSchemaLifecycle.Mode.VALIDATE`，拒绝pending/future/checksum冲突；不会创建schema、迁移历史或业务数据。错误只返回固定码，不输出连接异常和凭据。

`switch-release.mjs` 使用受信发布清单中的本地不可变镜像ID，确认四个实际运行角色匹配current。配置和容器的端口都必须与origin一致，防止把另一组的HTTP200误当成本组就绪。候选JAR检查通过后，停止应用、先重建main并等待内部HTTP，再重建共享命名空间的侧车，最后核对宿主HTTP与实际镜像。

`ready`只证明部署门槛。必须用真实账号读回原消息、已完成报告和预算，并验证后续写入。该流程是有停机窗口的单机发布，不会自动排空活动运行；失败保留现场，不会自动回退或删库。保留生成的镜像覆盖文件，后续重启也须继续传入它。

## 为什么保留两个发布版本

A为f0074f3的干净JAR，B增加重复模块在数据库访问前拒绝的CLI契约。前端分别保留早期课程图谱和已加入文件卷恢复节点的版本。这是明确的小版本差异，目的是检验真实不可变产物切换，而非将镜像改一个tag后宣称回退成功。业务schema和会话格式保持相同，不据此推断任意破坏性schema升级都可回退。

## 验收要求

按A→B→A→B检查实际镜像、CLI行为、相同会话详情、持久报告/预算及所选业务表指纹。兼容检查另用独立克隆数据库注入未来迁移记录，确认停服务前失败，原运行容器和正式数据不变。逐状态操作登录、历史选择、执行记录、语言和课程图谱，截图记录预期与实际。
