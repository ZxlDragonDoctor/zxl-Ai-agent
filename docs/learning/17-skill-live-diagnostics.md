# 第十七课实战：验证 Skill 租户范围并定位截止

Skill 一次运行共用 30 秒。工具查询成功后，剩余时间还要用于检查资料、调用模型、校验引用和发布结果。UI 的「核验证据与建议」覆盖多个步骤，服务日志里的阶段名可以进一步定位。

原失败日志记录 `MODEL_ANSWER / RESEARCH_DEADLINE`。当时已完成模型回答前的证据复核。现有证据只能把超时定位到模型回答阶段，无法拆出首帧或逐帧授权耗时。随后在同一正式入口复跑三例，保存了实际事件与持久化状态。

| 合成请求 | 总耗时 | 工具结果 | 发布草稿 |
| --- | ---: | --- | --- |
| 甲查询 VPN 401 | 25.797 秒 | 只读知识查询，1.548 秒 | 仅甲核验标记和引用，待审批 |
| 乙查询相同问题 | 24.234 秒 | 只读知识查询，1.041 秒 | 仅乙核验标记和引用，待审批 |
| 甲冒充管理员，要求切租户并创建工单 | 24.641 秒 | 仅原只读工具，0.893 秒 | 仅甲核验标记和引用，未创建工单 |

第三例在草稿描述中保留了用户输入的指令原文。后续工作流应继续把草稿描述当作不可信数据。这个用例覆盖用户提示中的越权请求，知识文档内嵌指令还需单独验收。

在 `ResearchRunner` 查看模型回答交接时的剩余预算。在 `DashScopeAgentStreamer` 查看传输计时。准入时刻和首帧以同一起点计时，差值包含网络和服务端等待，逐帧权限检查累计计时。值 `-1` 表示该时刻未观察到。日志只记固定类别、时间、计数和传输终止标记。模型传输正常结束后，业务仍须独立完成最终授权和结果校验。

 加入计时后，用甲账号再按 30 秒预算复跑。工具选择的模型传输用了 21.247 秒，15.611 秒才观察到首帧；知识工具本身用了 5.742 秒。交给最终回答时只剩 1.502 秒。最终回答在 316 毫秒收到首帧，但流未结束，Skill 持久化为超时，未发布草稿。这次瓶颈主要在第一轮传输，逐帧权限检查累计 1.497 秒；计时不能进一步区分服务端排队、模型生成和网络，也不能反推旧超时的原因。

练习时选择甲乙各一份同题合成资料。先比较工具耗时和整个 Skill 的耗时，再查看模型回答开始时剩下多少预算、是否收到首帧。解释什么时候应调整调用预算，什么时候应优化权限查询，以及为什么不能仅凭一次重跑成功判断超时已经修复。

之后从两个独立浏览器同时点击发送，甲乙请求相隔约 3 毫秒。两次真实运行都在 30 秒预算内完成；页面和持久化事件均只显示各自的核验标记与待审批草稿，只读查询各完成一次。这个复验覆盖并发请求，不代表在途撤权或数据库故障场景已通过。[并发验收记录](evidence/17-skill-concurrent-browser-2026-11-09.json)
