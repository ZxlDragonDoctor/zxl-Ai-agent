# 第 23 课续：运行额度与租户周期额度

运行额度回答“这一次任务最多受理多少调用”；租户周期额度回答“这批运行合起来还能预留多少”。两者必须在同一 PostgreSQL 事务检查并更新，不能先扣运行额度、再扣周期额度，否则第二步失败会留下半笔预留。

## 当前设计

正式 ScopedModelBudgetFactory 从可信 actor 取得租户，以 UTC 日期为周期。run 首次初始化固定所属周期，后续初始化与跨日重试不得重绑新周期或重置已用额度。TokenBudgetLedger 先锁 run，再锁该 run 对应的 period；所有结算采用相同锁顺序。新 run 共享当天的租户周期额度。

这是一种“运行创建日归集”策略，不是按每次实际发送日期切换的供应商账单日限额。跨日继续的旧 run 仍占原周期；既有运行的额度仍受 run 上限约束。不能将其宣传为任意自然日实际网络发送量的硬上限。

| 部署配置 | 默认值 |
| --- | --- |
| agent.usage.tenant-day-token-limit | 1000000 |
| agent.usage.tenant-day-call-limit | 1000 |

运行与周期额度同时约束预留加已知用量，调用受理次数在未发送释放后仍保留。实际 usage 高于估额时双层如实入账，后续调用被拒绝；UNKNOWN保留双层预留，不自动退款。它们都是 token 准入控制，不是金额预算或供应商账单。

## 必须核实的证据

真实 PG 验证不同 run 并发争抢同周期，失败方不残留单边扣额；运行额度先耗尽时周期无变化；释放、结算重放、超额和 UNKNOWN在两层一致；不同租户独立；注入时钟跨日后旧 run 留原周期、新 run 建新周期。V9只新增迁移，不修改旧V8历史。

旧账户若已经有受理记录但尚未归集周期，不得直接绑定空周期并继续消费。应拒绝并要求明确迁移/对账；不能通过上线新代码把已有用量变零。生产历史迁移与UNKNOWN人工对账仍需另行实施。

本文件说明设计与核实标准；具体通过数量、失败与截图以当批验收记录为准，不由代码存在推断。

## 代码定位与练习

阅读 ScopedModelBudgetFactory.initialize → TokenBudgetLedger.reserve → transition。说明为何同一事务内需要固定锁顺序，以及为何跨日已发送调用不能结算到新建的空周期。尝试把周期额度设为仅允许一个估额，在两个run同时请求时证明只有一个取得发送前预留。
