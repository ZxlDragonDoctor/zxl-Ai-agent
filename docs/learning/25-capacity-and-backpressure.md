# 第25课：容量、性能与背压

Agent请求不是一次数据库查询：一次运行会规划、等待角色、调用模型/工具、发布事件并等待实际清理。用户看到“结束”和底层资源可以再次使用，是两个时刻。容量教学先解释每层占用，再用固定版本和负载验证；不能用测试数、平均延迟或一张成功截图推断吞吐。

## 从Spring Boot接口走到执行资源

正式入口是 `FormalMultiAgentController`。HTTP202说明已接收运行标识，不说明执行成功。运行登记由 `RunRegistry` 保存，协调池负责运行流程，worker池负责阻塞动作，模型信号量限制模型并发。`RuntimeSettings` 分别定义运行线程/队列、worker线程/队列、模型并发和排队时限。队列满应拒绝，排队超时应停止，不能通过无限堆积内存“提高接收率”。

`ExecutionRuntime` 的 `runRejections` 与 `workerRejections` 区分拒绝层次；`workerQueuePeak` 是提交后采样的观测峰值，快速出队可能漏过瞬时峰值。它们是进程内数值，重启重置，不带租户或任务标签，不是某租户的用量账单。正式租户页面不应直接暴露其他租户的全局运行明细。

运行排队与模型排队都消耗同一总执行预算。`ExecutionControl` 检查总截止，`sweepRuns`/`sweepWorkerQueue` 清除过期待执行工作；取消不得使已经运行的供应商调用凭空消失。`RuntimeView.cleanupPending` 保留实际占用线索，任务/model lease及协调收尾完成前不能回收登记。

## 为什么还需要租户准入

全局有界队列只保护进程。若一个租户占满所有位置，其他租户仍会受影响。新实现用服务端 `TrustedRunContext.actor.tenantId`，在同一登记锁内限制同租户尚未完全回收的运行，默认 `agent.runtime.tenant-run-capacity=2`。同租户多账号共用上限；模型输入中的tenant字段不参与判断。

终态但仍持task/model/coordinator占用继续计数；完全清理的保留历史不占准入。新码 `AGENT_TENANT_CAPACITY_EXCEEDED` 对应HTTP429，页面提示等待本工作空间运行与清理完成。它是单实例有界准入，不是轮转调度或多实例全局配额；全局容量耗尽时，其他租户仍可能无法进入。真实双租户部署与参数对照尚需核验，不能仅凭登记单元测试宣称公平性已验收。

## 读懂本项目的负载实验

`scripts/lesson25/capacity-probe.mjs`采用闭环负载：每个虚拟用户等到本次终态再提交下一项，最多16次请求、4并发，只连明确本机HTTP端口，不自动重试POST。它分开记录提交延迟和按结果分类的终态延迟；观察超时不当成快速成功。由观察剩余时间导致的查询Abort与独立HTTP超时是不同结果，云端曾暴露该分类竞争，已有挂起HTTP回归。

有限实验结果见[阶段证据](../images/lesson25-capacity-2026-11-25/README.md)：固定8630d0e应用、a94c8a8探针，运行1+队列1、模型1、排队1000ms。基线1成功约29.4秒；6项/4并发中1完成、3异步容量失败、2排队超时。它们都是已接受运行的终态，不能改写为3个HTTP429。负载后再提交1项成功约19.7秒，证明该时刻仍可接收此类任务。

PG只读快照独立核对前7个运行、4笔SETTLED调用、4231 token、零预留/UNKNOWN。后续新任务不包含在该快照合计。零预留只证明账本状态，不证明线程、socket或供应商在途工作全零。代码任务没有检索，因此该实验不证明pgvector检索吞吐或完整知识业务性能。

## 有限调参如何证明因果

固定同一源码、数据、模型、并发、租户数和输入，每次只改一个参数。先写明预期：例如只增队列可能减少立即拒绝，但排队与尾延迟可能上升，不会自动增加模型处理能力。保存全部结果，包括失败、超时和样本数，恢复参数后验证新任务。至少分别测本地确定性模型夹具与少量真实供应商请求；后者有网络和模型波动，不用一次较快回答证明优化。

后续双租户真实HTTP已验证A超额429而B仍可完成，见阶段证据第17/18项；新版本独立PG核对也发现被拒请求残留零调用账户，已补[受守卫事务清理](25-rejected-run-budget-cleanup.md)，正式修复版重复HTTP拒绝尚需复验。不能将有缺陷的旧结果改写为全部通过。

本地组件[单参数前后及恢复对照](25-queue-capacity-comparison.md)已完成：固定1线程、6项提交，只改变队列1→4→1，立即拒绝4→1→4；未测延迟/吞吐，不代替真实HTTP性能基线。连接池、HTTP连接、数据库、消息总线、供应商限额都可能成为下一瓶颈；当前实验不覆盖全部组合，也不承诺生产P95或最大并发。完整容量基线与修复版验收仍未完成，用户的个人掌握状态保持独立。

## 阅读与练习顺序

1. 用 `RuntimeSettings` 画出运行/worker/model三层容量，解释线程与排队各占什么资源。
2. 阅读 `RuntimeCapacityMetricsTest` 和 `TenantRunAdmissionTest`，说明latch、受控时钟、lease分别证明了什么，哪些结论尚需真实HTTP。
3. 按[探针说明](../../scripts/lesson25/README.md)在隔离身份下跑1项，检查counts、样本数、终态、账本；再做有上限的并发实验。
4. 在页面切换容量失败、排队超时和完成记录，刷新并切语言；核对错误原因没有混淆。
5. 独立设计一次单参数对照，明确失败预期及恢复步骤，完成后才填写实测结果。

面试追问：为什么队列变大可能让P95更差？为什么202不是成功？公平Semaphore为什么不能自动保证租户公平？为什么取消后不能立即释放所有容量？多实例部署时该如何扩展租户准入且保持一致性？回答应引用当前代码和实验证据，并说明单实例/小样本边界。
